SciEval-Benchmark/SciEval 本身只是数据集加 rubric（273 份课程材料、3549 条带证据人工评分，数据邮件申请，CC BY 4.0），仓库无 API/服务端代码。评测引擎必须自建，bench 提供评分标准与校准样本。

设计基线（已确认的关键决策）

状态机放 OV 侧

kanban/资源目录存轮次状态，每次转换带产物版本号和报告 id。Vika 无状态执行，崩溃后状态不丢，换 runtime 可续跑。

课件用 HTML，不用真 PPT

write/edit 直接生成，绕开 python-pptx 的版式、动画、SmartArt 风险。评测对象是内容对教学指标与教师要求的符合度，不是版式还原度。

评测用规则 + LLM 混合

先做关键词/结构检查，再让模型按 13 项 EQuIP rubric 打分。成本低、可解释；拿到 3549 条人工评分后做 few-shot 校准，暂不微调。

为什么状态不放 Vika 里

崩溃恢复

Vika 进程或 Runtime 崩溃后，轮次状态、产物版本、报告 id 仍在 OV。新实例从 kanban 读到当前状态与待办，对照 workspace 实际文件后续做，不依赖内存推理现场。

可换 Runtime

Pi、Codex、Claude Code 的会话恢复能力不同。状态外置后，编排语义不绑定任何一个运行时，切换运行时只影响执行手段，不影响闭环判定。

一轮迭代的完整数据流

① 需求进入

教师在 IM 发教学设计、要求与多因素反馈；Connector 归一事件进 Core，建 job 与 subject

② 状态建档

OV kanban 建卡，状态置 pending_edit，写入 job_id、教师要求、评价指标与轮次上限

③ 改稿执行

Runtime 取卡与 skill 规范，workspace 内生成/修改 HTML，产物按 job_id+round 存不可变版本并记内容哈希

④ 提交评测

状态转 submitted；提交动作声明为 action 走 outbox，带幂等键；POC 经邮件/脚本提交 scieval

⑤ 评测回写

scieval 输出 13 维结构化报告；timer/邮件轮询拿到后写入 OV 资源目录并关联报告 id，状态转 evaluating→need_revision/done

⑥ 反馈再改

未达标则带着结构化反馈回到 ③，轮次 +1；达标、触顶或停滞则转 done/failed 并通知教师

↺ 反馈闭环：结构化报告（维度分 + 证据 + 页/段落定位 + 优先级 + 建议）是下一轮改稿的唯一输入；只有自然语言总分会导致多轮抖动不收敛

三条出站/入站通道

通道机制保证
消息类（通知、审批、报告投递）ActionService Outbox + idempotency_key权限校验、decision 新鲜度、重复发送去重

关键技术选择

规则 + LLM 混合评分

规则层先做关键词、结构、必备要素检查，确定性高、可解释；LLM 层按 rubric 锚点对开放性维度打分。先不微调，数据到位后再评估。

HTML 课件

Vika write/edit 原生生成，单文件自包含、可直接在 IM 与浏览器预览；版本 diff 清晰，内容符合度作为主评测对象。

email connector POC

scieval 结果发专用邮箱，复用现成 IMAP 轮询模板，零 Core 改造先验证闭环语义；验证通过再产品化为正式 Connector。

OV kanban 状态机

状态外置、版本与报告关联，崩溃可恢复、Runtime 可替换；skill 承载评分与改稿规范，资源目录存不可变产物。

Outbox + 幂等键

消息与提交类远端操作统一出站，带权限、decision 新鲜度校验和 idempotency_key；文件操作另做哈希级状态核对。

多实例隔离

一个 Core 只有一个共享会话，多教师多作业用独立 dataDir/workspace/OV 配置的多实例，或按 subject 严格隔离，防上下文串扰。

合规：Connector 0.2 仍在 schema 变更期、durable host 版本精确 pin，二开有跟随升级成本；AGPLv3 下做成面向学校的网络服务有源码披露义务，上线前过法务。

停机条件硬写进编排层，不靠提示词

判据规则出口
达标停机EQuIP 维度达标率达到阈值（主判据，HTML 渲染效果仅次要检查）done
迭代上限建议 ≤ 5 轮，超限不再自动改failed → 人工
停滞停机连续两轮无改善（考虑重复评测非确定性，加分数容差）failed → 人工
回归停机已达标维度在新一轮掉分failed → 人工
预算停机token / 时长 / 评测配额耗尽挂起或 failed

幂等与崩溃恢复：三个提交边界分开处理

输入层

稳定事件 id，先持久化可恢复记录再确认接收；重投相同 id 去重，区分"已接收"和"已处理"。

模型状态层

恢复已落盘的消息、工具调用与结果，已完成工具结果直接复用；重新推理可能生成不同调用 ID 的同一操作，不能只按 tool-call id 去重。

操作副作用层

执行前记录稳定操作 id、参数与前置条件，执行后记结果；结果不明时先核对实际效果再决定是否重做。

操作类型恢复方式
HTML 文件 edit记录修改前后哈希；已是目标状态就跳过，仍是原状态才修改，其他状态报冲突
产物版本按 job_id+round 存不可变版本，提交带内容哈希与幂等键，天然去重
评测提交 / 消息发送走 outbox 幂等键，重试前查已有结果与报告 id
任意 bash 多步操作不通用安全重放；效果无法核实时暂停并转人工核查，确保旧 Worker 与遗留子进程不再写入
最难的窗口：操作已生效但成功记录尚未落盘就崩溃。操作日志与文件系统、远端 API 不在同一事务，单加日志表消除不了这个窗口，所以严格恰好一次只限定在支持事务或幂等的操作上。

P0–P3 分阶段实施

P0 · 1–2 周 · 契约定调

发邮件申请 SciEval 数据集；定 scieval 提交/查询 API、结果 schema（13 维 + 证据 + 定位）、达标阈值与轮次策略；在 OV 建 skill、kanban 规范与产物目录规范；核对 13 项准则与本校教学评价指标的 gap，确定自定义维度。

P1 · 2–3 周 · 单教师单作业 POC

email connector + timer 轮询；Runtime 用 write/edit 生成 HTML 课件、python 只做辅助；kanban 记轮次跑通 pending_edit → done/failed；全量人工确认；先验证分数能否收敛，实测重复评测稳定性并定容差。

P2 · 3–5 周 · 产品化 Connector 与状态机固化

实现正式 scieval Connector（长轮询非聊天事件）；提交动作全走 outbox 幂等；状态机与停机判据固化在 OV 侧；多实例支持多教师并行；补齐崩溃恢复的哈希核对流程。

P3 · 分级自治与运营看板

按维度风险分级放开无人值守修改；加 token/时长成本看板与评测趋势图；数据集校准充分后评估评分模型微调；沉淀改稿规范回写 skill。

scieval 侧待确认四件事（P0 阻塞项）

接入形态

自建引擎对外提供 API 还是 webhook，或仅界面/邮件，决定 Connector 形态。

结构化能力

结果能否定位到具体页/段落，而非只有总分，决定闭环能否收敛。

评测确定性

同一产物重复评测的分数波动，决定停滞判据的容差设计。

时延与配额

单次评测时长与调用配额，决定轮询间隔、并行度与预算停机阈值。

主要风险优先级：① 反馈不够结构化导致不收敛；② LLM 评分不稳定；③ 提示注入（报告与课件原文不可信）；④ 多教师上下文串扰；⑤ AGPL 合规与二开跟随成本。PPT 风险已由"改 HTML"决策消除。
