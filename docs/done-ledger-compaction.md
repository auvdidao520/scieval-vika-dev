# DONE ledger: lossless compaction and explicit retirement proposal

Status: design only, based on PR #20 (07165ae). No compactor or retirement API is implemented. The current safe behavior retains every DONE row indefinitely. Do not enable deletion on the basis of age, the latest reservation, or a local sequence alone.

## Contract and limits

An arbitrary old accepted event may be reserved for the first time, retried, looked up, used in freshness checks or replay deduplication, or used as a SciEval report. `reserve` uses the complete row to create task input; the gateway compares identity and parses report `event_json`; other consumers query `connector_events` directly. A tombstone or digest alone cannot reconstruct the input, validate the report, or preserve all existing query semantics. There is no evidence that an upstream source has stopped retrying or that future grants cannot reference an unreserved origin. Therefore a time watermark, or min(active reservations), is not a safe deletion watermark.

Exact arbitrary-origin retries and bounded total storage for an unbounded stream cannot both be guaranteed: distinguishable events require retained information. Compression saves space, not the asymptotic growth, and may even increase the size of incompressible inputs. Privacy deletion is likewise incompatible with reconstructing deleted contents; it needs an explicit changed contract.

## Proposed first stage: lossless cold segments

Retain the complete logical row and every index needed for event identity, ordering, scope, authorization and deduplication. Move only cold, large fields into compressed versioned records keyed by seq, losslessly encoding *all* moved bytes, including NULL versus empty string. Initially target event_json and content only after auditing every direct SQL consumer and moving them behind a common reader; retain all other fields unchanged. Preserve unique `(connector_instance, event_id)` and AUTOINCREMENT high water. Decompression must exactly reproduce the old row for reserve, task input, accepted_scieval, route_accepted, inboundBySeq and all SQL consumers, including malformed historical data. Do not perform updates until every reader, migrations, diagnostics, backup and downgrade path are compatible. Do not use a view while unconverted writers or SELECT * callers depend on the physical table schema.

Use an in-database cold table with codec/version, original byte length, bounded decompressed length, payload and integrity digest. The index row and cold payload must move in one SQLite transaction. Readers reject unknown versions, size violations or checksum failures closed, without treating the event as absent or creating a new one. A bounded batch may move only DONE rows older than a configured cold threshold, regardless of whether already reserved. This threshold is a storage tier boundary, not a deletion or retry watermark. BEGIN IMMEDIATE serializes selection and migration with writes; transaction commit atomically publishes each batch. On restart SQLite rolls back uncommitted batches. Reprocessing committed batches is idempotent. Backups must use SQLite's consistent backup mechanism including WAL. Old binaries must fail closed when the schema version indicates cold rows; provide a tested full rehydration migration before rollback. Checkpoint and VACUUM are separate operations, may temporarily need extra disk, and are not secure erasure. Monitor failures, logical and physical bytes, oldest cold row, migration lag and available space; stop safely on disk-full.

## Optional second stage: explicit retirement, a contract change

No retirement is enabled by default. If the product later accepts a finite retry horizon, define per-origin-namespace epochs with authenticated producers and durable monotonically increasing contiguous sequence numbers. A signed/authorized producer seal S must guarantee no later event, retry, grant, delayed report or replay at or below S will ever be submitted; all consumers must durably acknowledge processing through S, all reservation, task and report references must be terminal under a documented policy, and all grants for the range must be revoked or rejected transactionally. A coordinator records the minimum acknowledged seal and epoch in the same durable authority as the deletion decision, then atomically advances a monotonic retired floor and deletes eligible records. Namespace membership, producer churn, gaps, snapshots and disaster recovery must be fenced; unknown or stale epochs fail closed. Old origins at or below the floor must return an explicit `origin_retired` and must never be treated as new. A seq allocated by this daemon is not proof of an upstream seal. Existing connectors do not provide these guarantees, so their floor remains unset and arbitrary-origin retry remains available.

Deduplication has its own requirement: a retired range can be rejected using the floor only if every future inbound event carries the authenticated namespace, epoch and producer sequence. Existing opaque event IDs do not satisfy that prerequisite; retain their dedupe evidence or reject the whole retired namespace. Restore ledger, seals and grants from one consistent snapshot, or freeze deletion and reconcile before accepting traffic. Regulatory deletion, expiration of backups and deletion of external copies require a separate policy; no claim of physical erasure follows from SQLite DELETE.

## Capacity and privacy

Let R be accepted events/day, B the mean combined event_json+content bytes, r compressed/original ratio and I the mean retained metadata plus indexes. Estimated logical bytes/year = 365 × R × (I + rB), before SQLite page fragmentation, WAL, backups and replicas. Example assumptions R=100,000/day, B=2 KiB, I=512 B and r=0.4 give 48.6 GB/year (decimal), versus 93.4 GB/year at r=1.0; savings 44.9 GB/year, not a bound. Real ratios must be measured on representative data, without exporting private content. At r=1.0 there is no gain; already-compressed or random data can expand. Retained indexes, other tables, duplicate content in task inputs, journals, OV and backups are excluded. Compression is reversible, not encryption or anonymization: names, identifiers and message contents remain sensitive. Limit access, encrypt storage/backups under managed keys, define retention separately for every copy, and assess WAL/freelist, logs and backups before claiming deletion.

## Acceptance before implementation ships

1. Inventory direct reads and writes; compare exact original and rehydrated rows, queries, SQL ordering, dedupe, authorization, first reservation of an old unreserved origin, reservation retry, activation and report route.
2. Kill/restart before and after batch commit, during migration and checkpoint; inject disk-full, corrupt/unknown codecs, decompression bombs and missing cold payload. Ensure fail-closed behavior, idempotence and no partial representation.
3. Exercise concurrent ingest, reservation, compaction and readers, schema upgrade, safe rollback, WAL-aware backup/restore and real SQLite database sizes. Verify no old binary can operate on migrated rows.
4. For retirement only, test gaps, late events, stale grants, all consumers, per-namespace epoch changes, reboot and inconsistent restore. Without those prerequisites, refuse to advance the floor.

The accompanying restart regression exercises PR #20's existing retention behavior, not the proposed compactor. The daemon recovery test uses simulated OV and does not establish exactly-once external side effects.
